# RAG 知识库的构建流程

## 1. 场景说明

当团队决定建设 RAG 系统时，第一步通常不是写 Prompt，而是把知识源加工成一套**可检索、可维护、可持续更新**的知识库。

一个可用的 RAG 知识库，不只是“把文档丢进向量库”。它至少要解决五件事：

- 从哪些知识源接入数据
- 如何清洗和标准化这些数据
- 如何把文档切成适合检索的 chunk
- 如何建立索引并支撑在线查询
- 如何做增量更新、回滚与质量监控

如果这五件事没有设计好，后面的召回、重排和回答质量上限都会被锁死。

## 2. 怎么做

可以把知识库构建流程拆成下面八步：

```text
1. 确定知识源范围
2. 采集并抽取原始内容
3. 清洗与结构标准化
4. 分块（Chunking）
5. 生成 Embedding
6. 建立检索索引
7. 写入元数据与版本信息
8. 建立增量更新与回滚机制
```

下面按工程顺序展开。

### 2.1 第一步：确定知识源范围

先定义什么内容应该进入知识库，什么内容不应该进入。

推荐优先级：

- 产品文档、帮助中心、FAQ
- 内部 SOP、流程规范、制度文档
- API 文档、技术说明、代码知识文档
- 高质量客服问答沉淀

不建议直接入库的内容：

- 高噪声聊天记录
- 未审核草稿
- 已过期但未标记版本的文档
- 彼此冲突又无权威来源的材料

这里最重要的设计思想是：**先做知识治理，再做知识接入**。

### 2.2 第二步：采集并抽取原始内容

不同知识源的接入方式不同，常见方式包括：

- 读取 Markdown / PDF / HTML / DOCX 文件
- 对接 CMS、Wiki、对象存储
- 抽取数据库中的结构化字段
- 拉取代码仓库中的 README、注释、规范文档

此阶段建议统一产出一个中间层数据结构，例如：

```json
{
  "doc_id": "product-refund-policy-v3",
  "title": "退款规则",
  "source": "help-center",
  "content": "...",
  "updated_at": "2026-05-22T10:00:00Z",
  "version": "v3"
}
```

这样后续清洗、切分、回滚都可以围绕稳定结构做，而不是被每种源格式绑死。

### 2.3 第三步：清洗与结构标准化

这一步的目标是让文档从“适合人读”变成“适合机器检索”。

至少应处理：

- 删除页眉页脚、导航栏、版权区、重复目录
- 保留标题层级、段落边界、列表结构
- 统一空白字符、换行、编码格式
- 提取来源、版本、业务域、权限标签等元数据

如果文档来自网页或 PDF，这一步尤其重要，因为原始文本噪声通常远超预期。

### 2.4 第四步：分块（Chunking）

切分的目标不是单纯压缩长度，而是在上下文窗口、召回粒度和语义完整性之间做平衡。

常见做法：

- 按固定 token 长度切分
- 按标题 / 段落 / 语义边界切分
- 配置 chunk overlap，保留上下文衔接

经验上建议优先遵循两条原则：

1. 一个 chunk 最好能独立表达一个局部完整语义
2. 不要让 chunk 大到包含多个主题，也不要小到只剩碎片句子

### 2.5 第五步：生成 Embedding

切分完成后，为每个 chunk 生成向量表示。此时建议同时保留：

- `chunk_text`
- `chunk_id`
- `doc_id`
- `title`
- `section_path`
- `updated_at`
- `source`
- `permissions`

一个实用的索引对象通常不是“纯向量”，而是“向量 + 原文 + 元数据”的组合。

### 2.6 第六步：建立检索索引

根据系统需求选择索引方案：

- 只做语义问答：可先上向量索引
- 兼顾关键词精准匹配：增加 BM25 或全文索引
- 业务过滤复杂：确保元数据过滤能力可用

工程上推荐从一开始就支持：

- Top-K 查询
- source / tenant / language / category 过滤
- 批量写入与批量删除
- 按 `doc_id` 回收旧版本 chunk

### 2.7 第七步：写入版本信息与元数据

如果不做版本控制，知识库很快会进入不可维护状态。

至少建议维护以下字段：

| 字段 | 用途 |
| --- | --- |
| `doc_id` | 同一文档的稳定标识 |
| `chunk_id` | chunk 级唯一标识 |
| `version` | 文档版本追踪 |
| `updated_at` | 判断增量更新时间 |
| `source` | 来源系统标识 |
| `permissions` | 权限过滤 |
| `section_path` | 回溯原始章节 |

这些字段不只是为了运维，也直接影响后续引用展示、权限控制与评测归因。

### 2.8 第八步：建立增量更新与回滚机制

真正可运营的知识库一定支持：

- 定时同步
- 按文档粒度增量更新
- 旧版本回滚
- 删除失效文档
- 重建单个分区或租户索引

推荐流程：

```text
发现文档更新
  ↓
重新抽取与清洗
  ↓
对同一 doc_id 重新切分与向量化
  ↓
删除旧 chunk
  ↓
写入新 chunk
  ↓
记录版本与更新时间
```

## 3. 为什么这么做

### 3.1 先治理知识源，再谈检索质量

很多团队一开始就盯着向量库和模型，结果最后发现主要问题是：知识源混乱、文档过期、内容互相冲突。RAG 的第一性问题不是模型，而是知识资产质量。

### 3.2 元数据是后续所有高级能力的基础

没有元数据，你几乎做不了：

- 权限隔离
- 来源引用
- 按业务域过滤
- 增量更新
- 评测归因

因此，知识库构建从第一天起就应该把元数据设计成一等公民。

### 3.3 增量更新比一次性导入更重要

一次性导入只是启动成本，长期维护成本才决定系统能不能活下来。没有增量更新机制的知识库，几乎注定会过时。

## 4. 关键取舍

### 4.1 先快上还是先完整治理

- **快速试点**：可以先接入少量高质量文档，验证主链路
- **正式上线**：必须补齐版本、权限、回滚与监控能力

### 4.2 统一全量重建还是增量更新

- 文档量小：全量重建简单直接
- 文档量大、更新频繁：必须做增量更新，否则成本过高

### 4.3 纯向量检索还是混合检索

- 语义问答场景强：可先纯向量
- 存在大量精确术语、编号、产品名：混合检索通常更稳

## 5. 常见坑

### 5.1 直接把原始 PDF 文本整段入库

这通常会导致严重噪声、标题断裂和召回异常，尤其是扫描件或排版复杂文档。

### 5.2 chunk 不保留来源信息

后续无法做引用展示、无法精确回滚，也无法排查具体是哪篇文档污染了结果。

### 5.3 更新时只追加，不清理旧版本

最终会产生重复 chunk、版本冲突和答案不一致问题。

### 5.4 忽略权限模型

如果不同用户看到的知识范围不同，入库阶段就必须设计权限标签，而不是等上线后补洞。

## 6. 一个推荐的最小工程方案

如果你要快速搭一个可试点的 RAG 知识库，推荐最小方案如下：

```text
知识源：高质量 Markdown / 帮助中心文档
清洗：保留标题层级，去掉导航噪声
分块：按段落 + 标题切分，适度 overlap
索引：向量检索 + 基础 metadata filter
元数据：doc_id / chunk_id / title / source / updated_at
更新：按 doc_id 做增量重建
```

这个方案足够轻，但已经具备后续演进空间。
