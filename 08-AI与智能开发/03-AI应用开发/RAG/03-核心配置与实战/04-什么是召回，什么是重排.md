# 什么是召回，什么是重排

## 1. 是什么

在 RAG 的在线检索链路里，召回（Recall）和重排（Rerank）是两个经常一起出现、但职责完全不同的阶段。

- **召回**：从大规模知识库里先找出一批“可能相关”的候选结果
- **重排**：在这批候选结果里，再进一步判断“哪些最相关”，并把排序调优到更适合后续回答

可以把它们理解成两层筛选：

```text
全量知识库
  ↓ 召回：先广泛找候选
候选结果集
  ↓ 重排：再精准排顺序
最终上下文候选
```

## 2. 为什么

把检索拆成两层，而不是一步到位，主要是因为大规模检索系统同时面临两个目标：

- 要够快，能够在海量数据里快速找到一批相关候选
- 要够准，能够把最适合当前问题的证据放到前面

单一阶段通常很难同时做到“又快又准”。于是系统会先用成本较低的方法做召回，再用更贵但更精细的方法做重排。

## 3. 怎么看

### 3.1 召回解决的是“别漏掉”

召回阶段的核心目标不是立刻找出最优答案，而是尽量保证：真正相关的内容至少进入候选集。

因此，召回更看重：

- 覆盖率
- 速度
- 候选广度

### 3.2 重排解决的是“别排错”

重排阶段的核心目标不是扩大范围，而是把候选集重新排序，让最有价值的内容排在前面。

因此，重排更看重：

- 相关性精度
- 前几条结果质量
- 上下文利用效率

## 4. 召回通常怎么做

常见召回方式包括：

- 向量召回：基于语义相似度查找 chunk
- 关键词召回：基于 BM25 或全文检索查找精确术语
- 混合召回：把两类结果合并
- 元数据过滤召回：先按租户、业务线、时间范围做约束

召回阶段的典型设计思想是：**先把可能对的内容捞上来，再说后面的判断。**

## 5. 重排通常怎么做

重排阶段会对召回出来的候选集做更精细的相关性判断。常见做法包括：

- 使用 Cross-Encoder 之类的重排模型
- 使用更强的 LLM 或判别模型对 Query 与 chunk 做相关性评分
- 结合业务规则做排序加权，例如：
  - 新版本文档优先
  - 官方文档优先
  - FAQ 命中优先

重排后的结果通常只保留前几条，进入最终上下文构造。

## 6. 两者的职责边界

| 维度 | 召回 | 重排 |
| --- | --- | --- |
| 目标 | 尽量找全候选 | 尽量排准顺序 |
| 关注点 | 覆盖率、速度 | 精度、Top-N 质量 |
| 处理对象 | 全量知识库 | 召回后的候选集 |
| 典型手段 | 向量检索、BM25、混合检索 | Cross-Encoder、规则排序、LLM 判别 |
| 常见失败 | 漏掉关键内容 | 相关内容排序靠后 |

理解这张表后，很多调优判断会更清楚：

- **查不到**，先看召回
- **查到了但排后面**，先看重排
- **查到了也排前面，但答案仍然差**，再看上下文构造和生成阶段

## 7. 常见失效模式

### 7.1 召回不足

表现：

- 用户问法稍有变化就查不到
- 同义表达或口语表达命中率很差
- 需要依赖专业术语时效果不稳定

常见原因：

- Embedding 模型不适配
- Chunking 设计不合理
- 没有 Query Rewrite
- 只依赖单一检索方式

### 7.2 重排不足

表现：

- 正确内容明明在候选里，但排名靠后
- Top1 / Top3 结果经常混入噪声
- 进入 Prompt 的片段相关性不稳定

常见原因：

- 缺少重排阶段
- 重排模型能力不足
- 业务规则未纳入排序逻辑
- 候选集本身过脏或过碎

## 8. 为什么很多系统需要两者结合

只做召回的问题在于：候选集中往往噪声较大，特别是 Top-K 设得稍大时，模型很容易被无关片段干扰。

只做重排的问题在于：如果召回阶段一开始就没把正确候选捞上来，重排再强也无能为力。

所以一个成熟的 RAG 系统通常会采用：

```text
Query
  ↓
多路召回 / 混合召回
  ↓
候选并集
  ↓
重排
  ↓
选择前 N 个高质量片段进入上下文
```

## 9. 实践建议

### 9.1 早期系统至少先把召回做好

没有召回覆盖率，再多精细排序都没有意义。PoC 阶段可以先用混合召回打底。

### 9.2 一旦进入真实业务，尽快补重排

因为用户对前几条结果的质量极其敏感，而重排正是提升 Top-N 体验最直接的手段之一。

### 9.3 评测时分开看召回指标和重排指标

不要把“最终回答不好”笼统归因为 RAG 效果差。要拆开定位：

- 是候选没找到？
- 还是候选找到了但没排前？
- 还是排前了但上下文构造差？
