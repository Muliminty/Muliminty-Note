# 什么是 RAG，它主要解决了什么问题

> 如果你还没有建立最小认知，建议先阅读上游基础文：[RAG 原理](../../01-AI基础理论/05-RAG%20原理.md)。本文不重复做入门解释，而是在专题语境下把 RAG 的定义、职责边界与工程价值讲清楚。

## 1. 是什么

RAG（Retrieval-Augmented Generation，检索增强生成）是一种把“外部知识检索”插入到 LLM 回答链路中的系统架构。

它的核心不是让模型参数变多，也不是让模型重新训练，而是让系统在生成回答前，先从外部知识源中找到与问题相关的证据，再把这些证据作为上下文交给模型。

从工程角度看，RAG 至少包含三层能力：

- **知识接入层**：文档、数据库、FAQ、内部规范、代码文档等外部数据源
- **检索编排层**：分块、Embedding、召回、重排、查询改写等中间链路
- **生成回答层**：把检索结果与用户问题拼接成 Prompt，交给 LLM 输出答案

因此，RAG 更准确的理解方式不是“一个算法”，而是“围绕知识接入和证据增强构建的一套回答系统”。

## 2. 为什么会出现

RAG 的出现，本质上是因为通用 LLM 在企业和产品场景中存在三个稳定短板：

### 2.1 参数知识不是实时知识

模型训练结束后，参数中的知识基本冻结。对于版本更新、制度变化、内部公告、最新 API 文档这类高频变化的信息，单靠模型参数无法保证时效性。

### 2.2 私有数据天然不在模型上下文里

企业内部 SOP、产品设计文档、业务规则、客户资料、代码仓库说明，默认都不在公开训练语料中。模型能力再强，也不会自动知道这些私有知识。

### 2.3 事实问答需要证据链，而不只是“会说”

很多业务问题不只是要求回答看起来合理，还要求：

- 能说明答案依据什么资料得出
- 能追溯到原始文档位置
- 当资料更新后，系统行为能够同步更新

这类需求天然推动系统从“参数记忆式回答”转向“证据驱动式回答”。

## 3. 它主要解决了什么问题

### 3.1 解决“模型不知道你自己的知识”

RAG 最大的价值，是把模型能力与业务私有知识连接起来。只要知识库构建得当，模型就能基于企业真实资料进行回答。

### 3.2 解决“知识更新成本过高”

如果问题本质是知识变化，而不是能力缺失，那么优先更新知识库通常比重新训练或微调更经济、更快上线。

### 3.3 解决“回答缺少可追溯性”

传统 LLM 输出很难天然附带证据。RAG 则可以把命中的文档片段、引用来源、命中顺序一起暴露出来，支撑审计、客服、知识问答等场景。

### 3.4 解决“事实型幻觉风险偏高”

RAG 并不能消灭幻觉，但可以显著改善“模型纯靠记忆瞎猜”的概率。前提是检索链路足够可靠，且生成阶段被约束为优先依据资料回答。

## 4. 怎么看：RAG 的正确心智模型

把 RAG 理解成“搜索系统 + LLM”的拼接还不够完整。更准确的心智模型是：

```text
用户问题
  ↓
查询理解（可选：改写、补全、消歧）
  ↓
候选召回（向量检索 / BM25 / 混合检索）
  ↓
结果重排（保留最相关证据）
  ↓
上下文构造（拼接片段、引用来源、控制长度）
  ↓
LLM 生成回答
```

这说明 RAG 的效果并不只由模型决定，而是由整条链路共同决定：

- 文档质量是否足够好
- 分块是否保留语义完整性
- 检索是否召回到了真正相关的片段
- 重排是否把最有用的内容送到了前面
- Prompt 是否要求模型基于证据作答

## 5. 能力边界

理解 RAG 时，必须同时理解它不解决什么问题。

### 5.1 它不替代模型本身的推理能力

RAG 负责把资料找出来，不负责替代模型做复杂推理。如果问题本身要求强推理、多步规划或复杂计算，仅有检索增强并不够。

### 5.2 它不等于微调

- **RAG** 主要解决知识接入与时效问题
- **微调** 主要解决风格、格式、领域习惯、行为模式问题

两者经常配合使用，但职责不同。

### 5.3 它不等于 Agent

RAG 重点在“先找资料再回答”；Agent 重点在“多步决策、工具调用、状态管理与任务执行”。RAG 可以是 Agent 的一部分，但不能混为一谈。

### 5.4 它不自动保证高质量答案

如果知识源过脏、切分失真、召回不准、Prompt 约束不够，RAG 依然会输出低质量答案。RAG 的收益高度依赖工程细节。

## 6. 与相邻概念的关系

### 6.1 与搜索系统

搜索系统侧重“找内容”；RAG 侧重“找内容后，让模型基于内容生成可消费的回答”。它继承了搜索系统的很多问题，也放大了上下文构造质量的重要性。

### 6.2 与向量数据库

向量数据库只是 RAG 里常见的底层存储与检索组件之一，不等于 RAG 本身。真正影响效果的，是知识表示、召回策略、重排与评测闭环。

### 6.3 与知识库问答产品

知识库问答是常见产品形态，RAG 是实现这类产品的一种主流架构。并不是所有知识库产品都必须用 RAG，但当前大多数高质量方案都离不开类似链路。

## 7. 工程落地中的关键判断

当你评估一个场景是否适合 RAG，可以优先问四个问题：

1. 回答是否必须依赖外部资料，而不是通用常识？
2. 这些资料是否会持续更新？
3. 结果是否需要来源可追溯？
4. 问题是否主要是知识接入问题，而不是模型推理能力问题？

如果四个问题中大部分答案是“是”，那么优先建设 RAG 往往比直接微调更合适。

## 8. 常见误区

- 误区一：接了向量库就等于做了 RAG
- 误区二：RAG 效果不好，一定是模型不够强
- 误区三：把 RAG 当作替代知识治理的捷径
- 误区四：忽略评测，只凭主观体验判断效果

真正可用的 RAG，靠的是知识源治理、链路设计和评测闭环，而不是单点堆料。
