# RAG 的完整链路与系统工作流程

> 如果你只需要最小认知，请先看 [RAG 原理](../../01-AI基础理论/05-RAG%20原理.md)。本文关注专题视角下的一整条系统链路，目标是回答“一个 RAG 系统究竟由哪些阶段组成，以及为什么每个阶段都会影响最终效果”。

## 1. 是什么

RAG 不是单点能力，而是一条把“知识准备、检索召回、上下文构造、回答生成、结果评估”串起来的系统工作流。

在实际工程中，RAG 至少包含两条相互关联的链路：

- **离线链路**：把外部知识加工成可被检索的结构化索引
- **在线链路**：在用户提问时，把最相关的证据找出来并驱动 LLM 生成回答

很多团队只关注在线问答体验，但真正决定效果上限的，往往是离线数据准备质量。

## 2. 为什么需要理解完整链路

如果只把 RAG 理解成“向量检索 + LLM”，会漏掉大量关键问题：

- 为什么同一批文档在不同系统里效果差异很大
- 为什么模型明明够强，但答案仍然偏离文档
- 为什么某些问题完全检索不到正确内容
- 为什么引入重排后效果明显提升

这些问题都不是单个组件能解释的，而是链路级问题。理解完整链路，才能知道该优化哪里。

## 3. 怎么看：两条主链路

## 3.1 离线链路：把知识变成可检索资产

离线链路通常包括以下步骤：

```text
知识源采集
  ↓
清洗与标准化
  ↓
分块（Chunking）
  ↓
向量化（Embedding）
  ↓
索引构建与存储
```

### 3.1.1 知识源采集

数据源可能来自：

- 产品文档
- 内部 SOP
- 帮助中心
- Wiki
- 数据库导出内容
- 代码注释与技术文档

第一层关键点不是“多”，而是“准”。错误、过期、重复、冲突文档会直接污染系统上限。

### 3.1.2 清洗与标准化

在进入检索链路之前，通常要先做：

- 去除模板噪声、页眉页脚、目录残留
- 统一编码、标题层级、段落结构
- 标记文档来源、版本、更新时间、权限信息

如果这一步做不好，后续召回命中的常常是无意义片段。

### 3.1.3 分块

分块的目标不是简单切短，而是在**长度可控**的前提下保住语义完整性。分块策略会直接影响：

- 向量表示是否稳定
- 检索粒度是否合适
- 送进上下文的内容是否干净

### 3.1.4 向量化

分块后的文本会被 Embedding 模型编码成向量，供相似度检索使用。此时需要关注：

- Embedding 模型是否匹配文本语言和领域
- 是否保留原文、标题、来源、元数据
- 是否需要混合索引而不只依赖向量

### 3.1.5 索引构建与存储

最终系统会把 chunk 与对应元数据写入检索存储中，常见方案包括：

- 向量数据库
- 搜索引擎
- 混合检索系统

此阶段的设计决定了后续在线检索的速度、过滤能力与可维护性。

## 3.2 在线链路：把问题变成有依据的回答

在线链路通常包括以下步骤：

```text
用户提问
  ↓
Query 预处理 / Rewrite（可选）
  ↓
候选召回
  ↓
重排
  ↓
上下文构造
  ↓
LLM 生成
  ↓
答案后处理与展示
```

### 3.2.1 用户提问

用户输入通常并不天然适合检索。常见问题包括：

- 指代不清
- 关键词过少
- 口语化过强
- 问题包含多个子意图

### 3.2.2 Query 预处理 / Rewrite

系统可以先对 Query 做标准化或改写，例如：

- 纠错与去噪
- 补全省略主语
- 把口语问法改成更适合检索的表达
- 将多意图问题拆成多个检索子问题

这一步不是必须存在，但在复杂业务里经常决定命中率。

### 3.2.3 候选召回

召回阶段的任务是：**先广泛找出一批“可能相关”的候选片段**。常见方式包括：

- 向量召回
- 关键词召回（BM25）
- 混合召回
- 基于元数据过滤的定向召回

召回阶段追求的是“不要漏”，而不是一步到位选出最优答案。

### 3.2.4 重排

当召回候选变多后，系统通常需要进一步判断“谁更相关”，于是进入重排阶段。重排常见目标有两个：

- 提升前几条结果的相关性密度
- 压缩无关噪声，节约上下文窗口

没有重排的系统，常见问题是“召回到了，但排得不对”。

### 3.2.5 上下文构造

这是很多系统里被低估但实际极关键的一步。系统需要决定：

- 选哪些片段进入 Prompt
- 片段顺序如何排列
- 是否附带标题、来源、时间、章节信息
- 是否合并相邻片段，减少上下文碎片化

一个检索命中了正确 chunk 的系统，仍然可能因为上下文拼接差而输出差答案。

### 3.2.6 LLM 生成

模型生成阶段的关键不是“让模型自由发挥”，而是通过 Prompt 明确约束：

- 优先依据给定资料回答
- 无法从资料中得到答案时明确说明
- 需要时输出引用来源
- 避免将外部常识与检索证据混写得不加区分

### 3.2.7 答案后处理与展示

对用户可见的最终结果，往往还要增加：

- 引用来源
- 高亮证据片段
- 可信度提示
- 权限控制
- 格式化输出

这一步决定产品体验是否“可用”，而不仅是模型是否“答出来”。

## 4. 系统工作流程总图

可以把一套较完整的 RAG 系统抽象成下面的工作流：

```text
离线：
文档采集 → 清洗标准化 → 分块 → Embedding → 建索引

在线：
用户问题 → Query Rewrite → 召回 → 重排 → 上下文构造 → LLM 回答 → 引用展示与评测回流
```

如果再加上长期运营视角，还应再补一条闭环：

```text
线上问题日志 → 标注与评测 → 发现失败样本 → 调整分块/召回/Prompt/重排 → 再上线验证
```

## 5. 每个阶段会影响什么

| 阶段 | 主要职责 | 典型失效表现 |
| --- | --- | --- |
| 知识采集 | 确保知识源真实、完整、可维护 | 回答基于过期或错误资料 |
| 清洗标准化 | 去除噪声、统一结构 | 命中到页眉页脚、目录碎片 |
| 分块 | 控制粒度并保留语义 | 命中片段残缺、上下文断裂 |
| Embedding / 索引 | 建立可检索表示 | 语义相似却无法命中 |
| 召回 | 先广泛找候选 | 漏召回、查不到关键内容 |
| 重排 | 把最相关内容顶上来 | 正确内容排名靠后 |
| 上下文构造 | 组织给 LLM 的证据 | 证据已命中但答案仍跑偏 |
| 生成 | 输出最终回答 | 乱补充、乱归纳、无引用 |
| 评测闭环 | 发现问题并持续改进 | 系统无法稳定优化 |

## 6. 与相邻概念的关系

### 6.1 与 Chunking

Chunking 属于离线链路的核心环节，直接决定后续检索粒度与上下文质量。

### 6.2 与 Recall / Rerank

Recall 与 Rerank 属于在线检索的核心阶段，一个负责尽量找全，一个负责尽量排准。

### 6.3 与 Query Rewrite

Query Rewrite 发生在召回前，主要提升“用户说的话”与“知识库里写的话”之间的匹配质量。

### 6.4 与评测体系

没有评测，就无法知道问题到底出在分块、召回、重排还是生成。RAG 必须被当作一条可度量的系统链路来运营。

## 7. 常见误区

- 误区一：链路中只要模型够强，其他都不重要
- 误区二：只做离线入库，不做线上日志分析与评测回流
- 误区三：把所有问题都归因给向量数据库
- 误区四：忽略上下文构造，默认“命中就一定能答好”
