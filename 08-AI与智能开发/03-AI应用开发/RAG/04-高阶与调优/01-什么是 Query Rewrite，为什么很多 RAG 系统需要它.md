# 什么是 Query Rewrite，为什么很多 RAG 系统需要它

## 1. 场景说明

很多 RAG 系统上线后会遇到一个很典型的问题：知识库里明明有答案，但用户一换种问法，命中率就明显下降。

这往往不是因为知识不存在，而是因为**用户表达**和**知识表达**之间存在偏差，例如：

- 用户问得过于口语化
- 关键词被省略
- 有多轮对话中的指代信息
- 一个问题里混了多个子意图

Query Rewrite 就是为了解决这类“问题没表达好，导致检索没命中”的问题。

## 2. 怎么做

Query Rewrite 指的是：在真正执行检索之前，先对用户输入做一层改写、补全或结构化，使其更适合检索系统理解。

一个典型链路如下：

```text
用户原始问题
  ↓
Query Rewrite
  ↓
更清晰、更完整、更适合检索的新 Query
  ↓
召回 / 重排
```

它并不是让系统“换个说法回答”，而是“换个更容易命中的说法去查”。

## 3. 为什么很多系统需要它

### 3.1 用户问题天然不是为检索写的

真实用户不会像写搜索词那样提问。他们常常：

- 说得很短
- 省略上下文
- 使用口语、代词、缩写
- 把多个问题混在一起

而检索系统通常更偏好语义清晰、边界明确、主语完整的问题表达。

### 3.2 知识库中的表达与用户语言不一致

文档可能写的是“订单退款规则”，用户却问“买完东西后不想要了怎么退”；文档写的是“租户隔离”，用户可能问“不同客户的数据会不会串”。

Query Rewrite 的作用，就是在“用户语言”和“知识语言”之间做一层桥接。

### 3.3 多轮对话会制造指代缺失

例如用户上一轮问“企业版支持审批流吗？”，下一轮只问“那导出呢？”。

如果系统直接检索“那导出呢”，几乎没有可检索性。Rewrite 后应变成“企业版是否支持导出功能”。

## 4. 常见改写方式

### 4.1 纠错与标准化

把错别字、大小写、缩写、口语噪声整理成更标准的表达。

### 4.2 主语补全

为省略主语、对象或上下文的问题补足必要信息，例如把“退款呢”补成“订单退款规则是什么”。

### 4.3 同义改写

把用户口语表达替换成更接近知识库文本的术语，例如：

- “退钱” → “退款”
- “权限隔开” → “权限隔离”
- “查历史版本” → “版本回滚 / 历史版本查看” 

### 4.4 多意图拆分

如果一个问题里同时包含多个子问题，可以拆成多个检索 Query，例如：

- “退款规则和发票重开怎么处理”
  - Query A：退款规则
  - Query B：发票重开流程

### 4.5 结构化改写

把自然语言问题改成更利于规则过滤的结构，例如提取：

- 产品线
- 用户角色
- 版本号
- 时间范围
- 功能模块

## 5. 为什么这么做

### 5.1 Query Rewrite 改善的是“命中机会”

它并不直接创造新知识，而是提升已有知识被正确找到的概率。

### 5.2 它常常比换模型更便宜

很多检索失败并不是模型理解不够，而是 Query 与知识表达不对齐。此时优先做 Query Rewrite，往往成本远低于直接更换更大模型。

### 5.3 它能显著改善长尾问法

标准问题通常即使不改写也能命中；真正受益最大的是那些口语化、模糊化、上下文依赖强的长尾问题。

## 6. 关键取舍

### 6.1 什么时候值得引入 Query Rewrite

满足以下条件时，通常值得引入：

- 问法差异很大，命中稳定性差
- 存在明显多轮对话场景
- 文档用词偏正式，用户问法偏口语
- 已确认知识库里有内容，但召回率仍偏低

### 6.2 什么时候不要过度依赖它

如果系统的主要问题是：

- 文档质量差
- Chunking 失真
- 候选召回策略弱
- 重排能力不足

那 Rewrite 只能局部补救，不能替代底层治理。

### 6.3 改写强度不能无限加大

改写过度会引入另一个问题：把用户真实意图改偏。尤其在专业领域和多义词场景里，过度补全可能产生误导。

## 7. 常见坑

### 7.1 把 Rewrite 当成“随便换个说法”

Rewrite 的目标是提升检索匹配，不是做语言美化。任何改写都应该围绕“更容易命中正确证据”展开。

### 7.2 引入 Rewrite 后不做可观测性

建议记录：

- 原始 Query
- 改写后 Query
- 两者对应的召回结果差异

否则很难判断改写到底帮了多少，还是反而改偏了。

### 7.3 用 Rewrite 掩盖知识库设计问题

如果基础文档和 Chunking 本身就有严重问题，Rewrite 只是把局部体验往上抬一点，无法从根上解决问题。

## 8. 一个实用落地策略

如果你要在项目里引入 Query Rewrite，推荐渐进式方案：

1. 先记录真实未命中样本
2. 从规则化改写和上下文补全开始
3. 观察召回率和 Top-K 质量是否改善
4. 再逐步引入模型化改写
5. 持续评估改写收益与误改率

这样能避免一上来就把链路复杂度拉满。
