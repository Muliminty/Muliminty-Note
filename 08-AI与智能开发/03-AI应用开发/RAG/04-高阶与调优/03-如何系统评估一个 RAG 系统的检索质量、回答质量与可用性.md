# 如何系统评估一个 RAG 系统的检索质量、回答质量与可用性

## 1. 场景说明

当 RAG 系统进入真实业务后，最容易出现的管理错觉是：

- 个别 Demo 看起来不错，就以为系统已经可用
- 用户抱怨结果不好，却不知道问题出在检索、重排还是生成
- 做了一堆优化，但无法量化到底有没有收益

要避免这种情况，必须把 RAG 当成一个可分层评估、可归因定位、可持续优化的工程系统来管理。

## 2. 怎么做

推荐按“三层评估 + 一条闭环”来组织整个评测体系：

```text
样本集设计
  ↓
检索层评测
  ↓
回答层评测
  ↓
系统层评测
  ↓
线上回流与迭代优化
```

下面分步骤展开。

### 2.1 先建设评测样本集

没有样本集，所有评估都会退化成主观感受。

一套最小可用样本集至少应包含：

- 用户问题
- 标准答案或参考答案
- 期望命中的证据文档 / chunk
- 问题类型标签
- 难度标签
- 业务域标签

推荐问题覆盖：

- 直接问答
- 多条件约束问答
- FAQ 变体问法
- 口语化问法
- 多轮指代问题
- 边界案例与异常情况

### 2.2 再做检索层评测

先不看模型回答，先判断系统有没有把对的证据找出来。

重点看：

- Recall@K
- Precision@K
- MRR / nDCG
- Top-K 候选是否包含关键证据

如果检索层已经失败，后面的回答层几乎不可能稳定成功。

### 2.3 再做回答层评测

在检索结果基础上，判断最终回答是否真的可用。

至少评估：

- 正确性（Correctness）
- 基于证据程度（Faithfulness）
- 完整性（Completeness）
- 引用准确性（Citation Accuracy）

这一层的目标是回答：**系统不只是找到了资料，而是真的把资料讲对、讲全、讲可信了。**

### 2.4 最后做系统层评测

即使检索和回答都不错，系统仍然可能因为太慢、不稳定、不可观测而无法上线。

因此还要评估：

- 总耗时与分阶段耗时
- 成功率 / 超时率 / 降级率
- 不同知识域之间的表现稳定性
- 线上用户是否真正完成任务

## 3. 为什么这么做

### 3.1 先拆层，再归因

RAG 的问题几乎从来不是“整体不好”这么简单，而是：

- 是 chunk 切坏了？
- 是召回没找全？
- 是重排没排准？
- 是 Prompt 没约束好？
- 是模型在乱补？

拆层评测的价值，就是让每个问题都能对应到可执行的优化方向。

### 3.2 指标必须和优化动作绑定

一个好的评测体系，不只是“报数字”，而是能指导决策：

- Recall 低 → 优先排查 Query Rewrite、Chunking、召回策略
- Precision 低 → 优先排查重排和噪声过滤
- Faithfulness 低 → 优先排查 Prompt 约束与引用拼接
- Completeness 低 → 优先排查上下文构造与 chunk 粒度

## 4. 一套推荐的评估流程

### 4.1 评测前：建立问题分桶

先给样本打标签，至少按下面维度分桶：

- 问题类型：定义类、流程类、规则类、异常类
- 问法形态：标准问法、口语问法、多轮问法
- 难度：简单、一般、复杂
- 知识域：产品、运营、技术、合规

这样做的价值是：当你发现系统整体分数下降时，可以快速定位是哪个桶出了问题。

### 4.2 检索评估：先看有没有找到

每条样本问题，记录：

- Top-K 候选内容
- 正确证据是否出现
- 第一个正确结果排第几
- 候选中噪声比例多高

如果这一步不合格，不建议直接进入回答优化，因为下游大概率只是建立在错误证据上“优化输出样式”。

### 4.3 回答评估：再看有没有答对

对每条问题，至少判断四件事：

1. 结论是否正确
2. 关键条件是否完整
3. 是否真的基于证据回答
4. 是否错误引用或乱补内容

如果资源有限，可以先采用人工抽样 + 明确评分 rubric；规模上来后，再逐步引入 LLM-as-a-judge 辅助。

### 4.4 系统评估：最后看线上是否可用

建议长期记录：

- P50 / P95 响应耗时
- 检索耗时、重排耗时、生成耗时
- API 错误率
- 兜底回答触发率
- 用户继续追问率 / 人工转接率

这些指标会决定系统能不能真正承担生产流量。

## 5. 关键取舍

### 5.1 先做离线评测，还是直接看线上反馈

- **离线评测**：适合做稳定对比和版本回归
- **线上反馈**：适合发现长尾问题和真实使用偏差

最佳实践不是二选一，而是两者结合。

### 5.2 人工评测还是 LLM 评测

- **人工评测**：准确度更高，但成本高
- **LLM 评测**：规模化更容易，但要防止评判漂移

推荐做法：先用人工建立 rubric，再用 LLM 做大规模初筛，保留人工抽检。

### 5.3 指标越多越好吗

不是。建议先建立“最小闭环指标集”，再逐步扩展，否则团队很容易陷入报表堆积但无决策价值。

## 6. 一个可落地的最小评测闭环

如果你现在就要给团队搭一套工程可执行的 RAG 评估流程，推荐最小版本如下：

### 6.1 数据准备

- 选 50～200 条真实高频问题
- 为每条问题标好参考答案和目标证据
- 按问题类型与难度分桶

### 6.2 检索评测

- 统计 Recall@5
- 统计 MRR
- 抽样检查 Top-5 噪声情况

### 6.3 回答评测

- 正确性：答对 / 部分正确 / 错误
- 完整性：是否遗漏关键条件
- Faithfulness：是否超出证据乱补

### 6.4 系统评测

- 记录总耗时与阶段耗时
- 记录失败率与兜底率
- 记录用户追问率

### 6.5 优化闭环

- 每轮只修改一类变量，例如分块、召回、重排、Prompt
- 每次改动后重新跑同一套样本集
- 对比分桶结果，而不是只看总体平均分

## 7. 常见坑

### 7.1 样本集全是标准问法

这样很容易把系统评得过于乐观，真实线上一遇到口语和省略表达就崩。

### 7.2 只看平均分，不看问题桶

平均分可能掩盖严重结构性问题，例如产品问题都很好，但规则类问题几乎全错。

### 7.3 每次同时改太多变量

如果一次同时调整 chunk、召回、重排和 Prompt，最后即使分数变好，也无法知道到底是哪一步起作用。

### 7.4 没有线上回流

离线评测集再完整，也无法覆盖真实用户持续变化的问法。线上日志回流必须进入长期机制。

## 8. 推荐的工程心态

系统评估不是为了“证明方案正确”，而是为了持续发现：

- 当前链路最短的木板是哪一块
- 这次优化到底带来了什么收益
- 哪些问题是基础数据治理问题，哪些是检索策略问题，哪些是生成约束问题

当团队形成这套评估文化后，RAG 才真正进入可运营状态。
