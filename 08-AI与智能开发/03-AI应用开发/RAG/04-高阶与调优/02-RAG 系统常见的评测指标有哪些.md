# RAG 系统常见的评测指标有哪些

## 1. 是什么

RAG 评测的核心目标，不是证明系统“看起来还行”，而是把问题拆成可以度量、可以归因、可以持续优化的指标体系。

一个成熟的 RAG 系统，至少要分别评测三层能力：

- **检索质量**：有没有把对的证据找出来
- **回答质量**：模型有没有基于证据给出正确、完整、可信的回答
- **系统可用性**：用户是否能稳定、快速、可控地使用这套能力

如果只评“最终回答像不像对”，你会很难知道问题到底出在哪一层。

## 2. 为什么

RAG 是多阶段系统，不同阶段需要不同指标来观察：

- 检索问题不能只靠主观阅读回答来判断
- 回答问题不能只看是否命中了文档
- 系统问题不能只看离线测试分数

因此，评测体系必须按阶段拆开。

## 3. 怎么看：三层指标框架

```text
检索层指标
  ↓
回答层指标
  ↓
系统层指标
```

你可以把它理解成：

- 检索层回答“证据找到了吗”
- 回答层回答“答案说对了吗”
- 系统层回答“这套东西在线上真的可用吗”

## 4. 检索层常见指标

### 4.1 Recall@K

表示在前 K 个检索结果中，是否包含目标证据。

它回答的问题是：**系统有没有把正确内容捞进候选集。**

适合判断：

- 召回覆盖率是否足够
- Query Rewrite 是否提升了命中机会
- Chunking 是否让证据更容易被找到

### 4.2 Precision@K

表示前 K 个结果里有多少是真正相关的。

它回答的问题是：**前几条结果有多干净。**

适合判断：

- 噪声是否过高
- 重排是否在提升 Top-K 纯度

### 4.3 MRR（Mean Reciprocal Rank）

衡量第一个正确结果排得有多靠前。排得越前，分数越高。

它回答的问题是：**系统是否能尽快把正确证据顶上来。**

### 4.4 nDCG@K

考虑排序位置与相关性等级的综合指标，适合有多级相关性标注的场景。

它回答的问题是：**整体排序质量是否合理，而不是只有“命中 / 未命中”二值判断。**

## 5. 回答层常见指标

### 5.1 Answer Correctness

判断最终答案是否正确。

可以通过人工标注或 LLM-as-a-judge 完成，但前提是评价规则明确，不能只凭“像不像对”。

### 5.2 Faithfulness / Groundedness

判断答案是否真正建立在给定证据上，而不是模型自己补出来的。

这是 RAG 里非常关键的指标，因为“答对了但不是基于证据”在很多业务场景里仍然是不合格的。

### 5.3 Completeness

判断答案是否覆盖了问题要求的关键要点。

很多 RAG 系统的常见问题不是完全答错，而是：

- 条件漏了一半
- 例外规则没说
- 只回答主流程，没回答边界情况

### 5.4 Citation Accuracy

如果系统展示引用来源，还需要评估：

- 引用是否真的支撑答案
- 引用是否对应正确文档或正确段落
- 是否存在“答的是 A，引用给的是 B”

## 6. 系统层常见指标

### 6.1 Latency

包括：

- 检索耗时
- 重排耗时
- 总回答耗时

这是判断线上体验是否可用的基础指标。

### 6.2 Success Rate

表示在一段时间内，系统能够稳定完成问答请求的比例。

包括但不限于：

- 检索成功率
- 模型调用成功率
- 整体链路成功率

### 6.3 Fallback Rate

当系统无法可靠回答时，是否触发了“未找到依据”“建议人工处理”等兜底策略。这个指标可以帮助你判断系统到底是在“谨慎失败”，还是“带幻觉地乱答”。

### 6.4 User Satisfaction / Task Success

如果系统最终服务真实用户，还要观察：

- 用户是否点击了引用来源
- 用户是否继续追问澄清
- 用户是否采纳答案完成任务
- 人工转接率是否下降

这些指标更贴近业务效果。

## 7. 关键判断：不同指标分别能发现什么

| 指标 | 主要回答的问题 |
| --- | --- |
| Recall@K | 对的证据有没有被找进来 |
| Precision@K | 前几条结果里噪声多不多 |
| MRR | 正确结果排得靠不靠前 |
| nDCG@K | 排序整体是否合理 |
| Answer Correctness | 最终答案是否正确 |
| Faithfulness | 答案是否基于证据 |
| Completeness | 答案是否讲全了 |
| Citation Accuracy | 引用是否准确支撑答案 |
| Latency | 用户等待时间是否可接受 |
| Success Rate | 系统是否稳定可用 |
| User Satisfaction | 业务侧是否真正认可结果 |

## 8. 常见误区

### 8.1 只看回答对不对，不看证据链

这会掩盖大量潜在风险，尤其在合规、客服、企业知识问答场景里。

### 8.2 只看 Recall，不看排序质量

正确结果即使被召回，如果永远排在第 20 条，实际价值也很有限。

### 8.3 只做离线评测，不看线上可用性

离线数据集分数很高，并不意味着线上用户问法就稳定命中。

### 8.4 指标太多但没有归因路径

指标不是越多越好，关键是每个指标都要能指向具体优化动作。

## 9. 实践建议

如果你要从零建立一套 RAG 评测体系，建议最小起步组合为：

- 检索层：Recall@K、MRR
- 回答层：Correctness、Faithfulness、Completeness
- 系统层：Latency、Success Rate

这套组合已经足以覆盖大多数第一轮优化判断。
