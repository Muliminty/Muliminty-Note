# A2A 协议完整指南

> Agent2Agent（A2A）是由 Google 发起并捐赠 Linux 基金会的开放协议，为跨框架、跨厂商的 AI 智能体提供统一的通信与协作标准。

## 📖 概述

### 什么是 A2A？

**A2A（Agent2Agent）** 是一个开放的 AI 智能体间通信协议，旨在让构建在不同框架（LangGraph、CrewAI、Semantic Kernel 等）、运行在不同服务器上的 AI Agent 能够相互发现、派发任务、交换数据和协同工作。

- **发起方**：Google（2025 年 4 月 Google Cloud Next 大会公布）
- **当前归属**：Linux 基金会（已捐赠，Apache 2.0 许可证）
- **核心目标**：为 Agent 提供「通用语言」，打破异构 Agent 之间的通信孤岛
- **定位**：Agent ↔ Agent 的公共互联网，与 MCP（Agent ↔ Tool）互补

### 核心价值

1. **跨异构协作**：不同框架、不同大模型的 Agent 按统一标准收发消息，无需关心对方底层实现
2. **能力自动发现**：通过 Agent Card 声明能力，客户端自动探测远程 Agent 能做什么
3. **长任务原生支持**：协议设计以异步优先，天然适配人机协同、长时间运行的任务
4. **不透明执行**：Agent 协作时无需暴露内部状态、记忆或工具实现，保障安全与知识产权

## 🏗️ 核心概念

A2A 协议围绕以下核心概念构建：

| 概念 | 说明 |
|:---|:---|
| **A2A Client** | 发起请求的应用程序或 Agent，代表用户或另一系统向 A2A Server 发送任务 |
| **A2A Server（Remote Agent）** | 暴露 A2A 兼容端点的 Agent 系统，负责处理任务并返回结果 |
| **Agent Card** | JSON 元数据文档，描述 Agent 的身份、能力、技能、服务端点及认证要求 |
| **Message** | Client 与 Remote Agent 之间的一次通信回合，包含角色（`user` / `agent`）和一组 Part |
| **Task** | A2A 的基本工作单元，具有唯一 ID 和状态生命周期 |
| **Part** | Message 或 Artifact 中的最小内容单元，可为文本、文件引用或结构化数据 |
| **Artifact** | Agent 完成任务后生成的输出（文档、图片、结构化数据等），由 Part 组成 |

### Task 生命周期

```
TASK_STATE_WORKING  →  TASK_STATE_INPUT_REQUIRED  →  TASK_STATE_WORKING
                                ↓
         TASK_STATE_COMPLETED / FAILED / CANCELED / REJECTED
```

- **非终态**：`WORKING`（处理中）、`INPUT_REQUIRED`（等待人工输入）、`AUTH_REQUIRED`（等待授权）
- **终态**：`COMPLETED`、`FAILED`、`CANCELED`、`REJECTED`——到达终态后 Task 不再接受新消息

### 协议分层

```
┌─────────────────────────────────────────┐
│  Layer 1: Canonical Data Model          │
│  Task / Message / AgentCard / Part / …  │
├─────────────────────────────────────────┤
│  Layer 2: Abstract Operations           │
│  Send Message / Get Task / Cancel / …   │
├─────────────────────────────────────────┤
│  Layer 3: Protocol Bindings             │
│  JSON-RPC / gRPC / HTTP+REST            │
└─────────────────────────────────────────┘
```

三层架构确保核心语义在所有协议绑定下保持一致，同时允许新的传输绑定加入而不改动数据模型。

## 🔍 Agent Card 能力发现

### 工作原理

每个 A2A Server 对外发布一个 **Agent Card**——JSON 格式的元数据文档，描述：

- **身份信息**：Agent 名称、描述、版本
- **能力声明**：支持的操作（流式传输、推送通知、扩展 Agent Card 等）
- **技能列表**：Agent 能完成的具體任務類型
- **服务端点**：A2A 接口 URL
- **认证要求**：支持的认证方案（OAuth 2.0、mTLS 等）
- **交互模式**：支持的媒体类型（文本、文件、结构化数据）

Client 在发起任务前，先获取 Agent Card 了解对方能力，再决定如何构造请求。这类似于微服务体系中「服务注册与发现」的角色。

### 获取方式

A2A 规范定义了 `Get Agent Card` 操作（Layer 2 抽象操作），具体绑定到各传输协议（JSON-RPC 方法、HTTP GET 端点等）。协议委员会正在讨论将发现路径标准化为类似 `/.well-known/` 的约定，以进一步降低自动发现门槛。

## 📡 三种通信模式

### 1. 同步请求/响应（Send Message）

适用于短任务，Client 发送 Message → Server 返回 Task 或直接返回 Message。

- **阻塞模式**（`returnImmediately: false`，默认）：等待 Task 到达终态或中断态后返回
- **非阻塞模式**（`returnImmediately: true`）：立即返回 Task 对象，Client 后续通过轮询或推送获取结果

### 2. 流式传输（Send Streaming Message / Subscribe to Task）

适用于需要实时反馈的场景，基于 SSE（Server-Sent Events）实现。

- **Send Streaming Message**：发起任务并建立流式连接，持续接收 `TaskStatusUpdateEvent`（状态变更）和 `TaskArtifactUpdateEvent`（产出物增量更新）
- **Subscribe to Task**：订阅已有 Task 的更新流，从当前状态开始接收后续事件
- 流在 Task 到达终态时自动关闭

### 3. 推送通知（Push Notification / Webhook）

适用于长耗时、客户端可离线的场景。

- Client 通过 `Create Push Notification Config` 注册 Webhook URL
- Task 状态变更时，Server 主动向该 URL 发送 HTTP POST（载荷为 `StreamResponse`）
- Client 可通过 `List / Get / Delete Push Notification Config` 管理配置

### 模式选择指南

| 场景 | 推荐模式 |
|:---|:---|
| 简单查询、即时任务 | 同步 Send Message（非阻塞） |
| 需要实时进度的任务 | Streaming（Send Streaming Message） |
| 长耗时、客户端需离线 | Push Notification |
| 已有 Task，需要监控后续状态 | Subscribe to Task |
| 已断开连接，回来查询结果 | Get Task（轮询） |

## 🔌 A2A vs MCP：互补而非竞争

A2A 和 MCP（Model Context Protocol）经常被放在一起讨论，但它们解决的是不同层次的问题：

| 维度 | A2A | MCP |
|:---|:---|:---|
| **通信对象** | Agent ↔ Agent | LLM ↔ 工具/数据源 |
| **定位** | Agent 的「公共互联网」 | Agent 的「工具接口标准」 |
| **核心问题** | 不同 Agent 之间如何协作 | Agent 如何调用外部工具和获取数据 |
| **提出方** | Google（2025.4） | Anthropic（2024.11） |
| **典型场景** | 招聘 Agent → 简历解析 Agent → 排期 Agent 链式协作 | Claude 读写本地文件、查询数据库、调用 API |

**关系**：A2A 和 MCP 是互补的。一个 Agent 可以同时装备 MCP（连接工具）并通过 A2A（与其他 Agent 通信）。Google 官方的描述是：

> Build with ADK (or any framework), equip with MCP (or any tool), and communicate with A2A, to remote agents, local agents, and humans.

### 易混淆：金融 A2A

「A2A」在金融领域另有所指——**Account-to-Account（账户对账户转账）**，指不经卡组织（Visa/银联）的银行账户间直接清算，代表系统包括印度 UPI、巴西 Pix、中国网上支付跨行清算系统（IBPS / 超级网银）等。本文讨论的 A2A 是 **Agent-to-Agent**，两者是完全不同领域的概念，仅缩写相同。

## ⚠️ 安全设计

A2A 定位为企业级协议，安全设计融入核心规范：

1. **认证**：Agent Card 的 `securitySchemes` 字段声明支持的认证方案（OAuth 2.0、mTLS 等）
2. **不透明执行**：Agent 协作时**不暴露**内部状态、记忆或工具实现——仅基于声明式能力交互
3. **授权范围**：实现需对 Task 访问做适当的授权范围控制，确保 Client 只能访问被授权的 Task
4. **扩展 Agent Card**：认证后可获取更详细的 Agent Card，支持按权限分级暴露能力
